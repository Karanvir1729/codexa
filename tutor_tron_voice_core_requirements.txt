Tutor-Tron Voice Agent - Core Requirements

1. Product Goal

Build Tutor-Tron Voice as a production-grade, self-improving voice tutoring system for the voice agent hackathon.

The system must not be positioned as a simple AI voice demo or "ChatGPT with voice." It must be a multi-agent tutoring system where every student interaction can update shared context, detect teaching failures, generate evals, and improve the next similar tutoring session.

Core one-liner:

Tutor-Tron turns every tutoring failure into updated context, a reusable teaching rule, and an eval case so the same mistake is not repeated with the next similar student.


2. Hackathon Alignment

The system should clearly map to the hackathon themes:

- Production-grade voice agent, not a demo.
- Low-latency, scalable voice infrastructure.
- SOTA open-weights model usage or customization, ideally NVIDIA-accelerated.
- AWS/NVIDIA-compatible deployment story.
- Pipecat/Daily-based real-time voice pipeline.
- Automated testing and evaluation loop inspired by Cekura.
- Auto-improvement from conversations, failures, transcripts, latency data, and eval results.
- Persistent learning across individual students and similar-student cohorts.


3. MVP Scope

Start with one narrow subject so the system loop is easy to prove.

Recommended demo subject:

- Grade 12 probability.
- Binomial vs hypergeometric distributions.
- Main pitfall: student thinks "two outcomes" always means binomial.
- Correct repair: explain replacement and independence before formulas.


4. Real-Time Voice Tutor Requirements

The voice tutor must:

- Support real-time voice conversation with low latency.
- Allow the student to interrupt mid-explanation.
- Respond naturally without long pauses.
- Maintain context across the full session.
- Switch between explaining, questioning, hinting, testing, and reviewing prerequisites.
- Ask diagnostic questions instead of only lecturing.
- Check whether the student actually understands before moving on.
- Adapt tone, speed, depth, and strategy based on the student's state.
- Explain concepts using multiple styles, including analogy, formula, worked example, visual description, and step-by-step reasoning.


5. Student State Engine Requirements

The system must maintain a live student state during the call.

Track:

- Current topic.
- Current sub-skill.
- Mastery score.
- Confidence level.
- Confusion level.
- Recent mistakes.
- Active pitfall.
- Whether the student is understanding, guessing, or memorizing.
- Strategies that worked for this student.
- Strategies that failed for this student.
- Whether the student needs review, practice, or deeper explanation.

The state must update after every student response, not only after the session ends.

Example state:

{
  "topic": "probability_distributions",
  "sub_skill": "binomial_vs_hypergeometric",
  "confidence": "low",
  "confusion": "high",
  "active_pitfall": "does_not_understand_without_replacement",
  "best_strategy": "replacement_first_explanation"
}


6. Common Pitfall Detection Requirements

The system must maintain and use a library of common student pitfalls by subject, topic, and sub-skill.

The pitfall detector must:

- Match student responses to likely misconceptions.
- Detect when the student is using the wrong concept.
- Detect when the student is applying a formula blindly.
- Detect when the student understands the answer but not the reasoning.
- Detect repeated questions or repeated wrong answers.
- Detect hesitation, uncertainty, vague confusion, or shallow agreement.
- Detect when the tutor's previous explanation failed.
- Tag each failure with a pitfall ID.

Example pitfall:

{
  "pitfall_id": "binomial_vs_hypergeometric_001",
  "trigger": "student treats no-replacement draw as independent",
  "repair_strategy": "explain replacement before formula",
  "avoid_strategy": "formula_first"
}


7. Similar-Student Learning Requirements

The system must learn across students.

It must:

- Group students by similar learning and misconception patterns.
- Retrieve past failures from similar students.
- Retrieve teaching strategies that worked for similar students.
- Avoid strategies that failed for similar students.
- Update cohort-level misconception patterns.
- Update cohort-level strategy rankings.
- Let one student's failure improve the next similar student's session.

Core requirement:

If a strategy fails for one student, future similar students should automatically receive a better strategy.


8. Teaching Strategy Memory Requirements

The system must store multiple teaching strategies per concept.

It must:

- Store candidate strategies for each concept and pitfall.
- Track which strategy was used.
- Track whether the strategy worked.
- Rank strategies by success rate.
- Select strategies based on student profile, active pitfall, and similar-student evidence.
- Generate new strategy variants when existing strategies fail.

Example strategies:

- diagnostic_question_first
- analogy_first
- worked_example_first
- formula_first
- replacement_check_first
- visualization_first
- prerequisite_review_first
- socratic_hinting
- slow_step_by_step


9. Multi-Agent Architecture Requirements

Tutor-Tron must be designed as an interconnected multi-agent system with a shared context layer.

Required agents or services:

1. Voice Tutor Agent
2. Student State Agent
3. Pitfall Detection Agent
4. RAG Retrieval Agent
5. Similar-Student Agent
6. Teaching Strategy Agent
7. Evaluation Agent
8. Auto-Improvement Agent
9. SCIP Optimization Layer
10. Tutor Orchestrator
11. Dashboard API
12. Dashboard UI

All agents must read from and write to shared context.

Shared context should include:

- student_state
- session_state
- active_pitfalls
- cohort_patterns
- teaching_strategy_scores
- open_alerts
- eval_results
- system_metrics


10. RAG Layer Requirements

RAG must be used for teaching memory, not only textbook lookup.

Required RAG indexes:

1. Curriculum RAG
   - Retrieve curriculum-aligned definitions, formulas, examples, and explanations.
   - Ground tutor responses in trusted lesson content.

2. Misconception RAG
   - Retrieve known pitfalls for the current topic.
   - Retrieve repair strategies that worked.
   - Retrieve failed strategies to avoid.

3. Student Memory RAG
   - Retrieve the student's past struggles.
   - Retrieve mastered concepts.
   - Retrieve explanations that worked or failed for the student.

4. Cohort RAG
   - Retrieve patterns from similar students.
   - Retrieve best-performing strategies by student cluster.
   - Retrieve common mistakes by grade, course, topic, and learning style.

5. Eval RAG
   - Retrieve past eval cases for the same topic.
   - Retrieve generated tests from previous failures.
   - Compare current tutor behavior against known good and failed responses.

6. Strategy RAG
   - Retrieve candidate teaching strategies.
   - Retrieve strategy success rates.
   - Feed strategy options to the SCIP layer.

Recommended vector database:

- Qdrant, with separate collections for curriculum chunks, misconception library, student memory, cohort patterns, strategy outcomes, and eval cases.


11. Alert System Requirements

Every agent should be able to emit alerts into the shared event bus.

Example alert types:

- student_confusion_spike
- repeated_wrong_answer
- pitfall_detected
- strategy_failed
- strategy_succeeded
- student_disengaged
- latency_too_high
- eval_regression
- low_mastery_topic
- similar_student_warning
- need_new_eval_case
- rag_low_confidence
- asr_uncertain_transcript
- tts_failure

Each alert should include:

- alert_id
- type
- severity
- student_id
- session_id
- topic
- pitfall, if relevant
- candidate actions
- timestamp


12. SCIP Optimization Layer Requirements

SCIP should be a fast decision layer, not the tutor itself.

It must:

- Receive alerts from agents.
- Decide what to optimize right now.
- Select the highest-value next action under constraints.
- Choose whether to switch teaching strategy.
- Choose whether to ask a question, explain, review prerequisites, generate an eval, or update memory.
- Use a strict time limit, such as 50 to 150 ms.
- Fall back to a heuristic policy if optimization times out.

Optimization targets may include:

- Maximize student understanding.
- Maximize misconception repair.
- Maximize expected learning gain.
- Maximize future reuse value.
- Minimize latency.
- Minimize cognitive load.
- Avoid unnecessary strategy switching.

Example constraints:

- response_latency <= 800 ms
- do not switch strategy too often
- must address high-severity pitfalls
- avoid formula-first strategy when confusion is high
- generate eval only if failure confidence is high
- promote strategy only if eval score improves


13. Failure-to-Improvement Loop Requirements

Every failed tutoring interaction must produce at least one learning artifact.

Possible artifacts:

- New pitfall tag.
- Updated student context.
- Updated cohort pattern.
- New teaching rule.
- New eval test case.
- New strategy ranking.
- New guardrail for future responses.
- New reusable explanation strategy.

Core requirement:

A failed explanation should never just be logged. It must update the system.


14. Auto-Improvement Pipeline Requirements

The system must improve through memory, rules, strategy updates, retrieval, and evals. It should not depend on live model fine-tuning during the hackathon.

Pipeline:

1. Detect failed session or failed explanation.
2. Extract reason for failure.
3. Identify pitfall and ineffective strategy.
4. Generate an improvement proposal.
5. Add or update a teaching strategy.
6. Generate an eval case.
7. Run eval against old and new strategy.
8. Promote the new strategy only if it performs better.
9. Use the improved strategy for future similar students.


15. Evaluation Harness Requirements

The system must include automated evaluation, not subjective "sounds good" judging.

It must:

- Simulate different student personas.
- Simulate common wrong answers.
- Simulate vague confusion.
- Simulate repeated misunderstanding.
- Simulate students who say "yes" but still do not understand.
- Score tutor responses for correctness, clarity, patience, usefulness, and recovery.
- Score whether the student reached understanding.
- Measure whether the tutor asks good follow-up questions.
- Measure whether the tutor over-explains or under-explains.
- Generate new eval cases from real failed conversations.
- Re-run evals after strategy updates.
- Track before and after performance.

Example personas:

- confused student
- distracted student
- overconfident student
- ESL student
- anxious student
- test-prep student


16. Data and Memory Requirements

The system must store:

- Session transcripts.
- Audio metadata, where useful.
- Topic-level mastery scores.
- Student state changes.
- Misconception tags.
- Teaching strategies used.
- Outcomes of each strategy.
- Strategy success rates.
- Latency and voice interaction metrics.
- Eval cases.
- Eval results.
- Cohort-level misconception patterns.
- Auto-generated teaching rules.
- Version history of teaching strategies.


17. Infrastructure Requirements

Recommended stack:

- Python FastAPI backend services.
- Pipecat for real-time voice runtime.
- Daily/WebRTC for voice transport.
- NVIDIA Riva or another streaming ASR option if aligning with NVIDIA.
- Streaming TTS.
- Redis Streams for event bus.
- Redis for distributed cache, session state, rate limits, and recent context.
- Postgres for persistent relational data.
- Qdrant for vector search and RAG.
- SCIP/PySCIPOpt service for optimization decisions.
- Docker Swarm for hackathon deployment.
- Traefik or Caddy/Nginx for routing.
- MinIO or S3 for object storage.
- Prometheus, Grafana, and OpenTelemetry for observability.
- React dashboard.


18. Redundancy Requirements

The system should be designed for replicated stateless services.

Suggested replicas:

- voice-gateway: 2 replicas
- tutor-orchestrator: 3 replicas
- student-state-agent: 2 replicas
- pitfall-agent: 2 replicas
- rag-agent: 2 replicas
- scip-agent: 2 replicas
- dashboard-api: 2 replicas
- eval-agent: 1 to 2 replicas
- auto-improvement-agent: 1 replica

Stateful services for hackathon:

- Redis with persistence.
- Postgres with snapshots or managed database.
- Qdrant with persistent volume.
- MinIO or S3 for transcripts, audio, and eval artifacts.

Production framing:

- Managed Redis or Redis Sentinel.
- Postgres primary plus read replica.
- Qdrant distributed replication.
- S3 durable object storage.
- Multi-node Docker Swarm.


19. Caching Requirements

Use aggressive caching because voice latency matters.

L1 in-process cache:

- Current session state.
- Recent transcript window.
- Current RAG chunks.
- Current strategy decision.
- Active pitfall labels.

L2 Redis cache:

- Session state.
- RAG query results.
- Embedding results.
- Strategy scores.
- Eval scores.
- Rate limits.
- Recent cohort lookups.
- TTS phrase cache metadata.

L3 vector retrieval cache:

- Common topic retrievals.
- Common misconception lookups.
- Common strategy lookups.

L4 TTS cache:

- Common tutor phrases.
- Reusable explanation fragments.
- Short confirmation and transition phrases.

L5 eval cache:

- Reuse eval results when the same eval case runs against the same strategy version.


20. Dashboard Requirements

The dashboard must show the improvement loop clearly.

It should display:

- Live student state.
- Current topic and sub-skill.
- Detected pitfall.
- Selected teaching strategy.
- Similar-student patterns.
- Strategies that worked and failed.
- Strategy success rates.
- Failed tutor responses.
- Generated eval cases.
- Eval results.
- Auto-generated teaching rules.
- Before and after improvement.
- Cohort-level misconception trends.
- Latency and voice quality metrics.
- Open alerts.
- SCIP decisions.


21. Demo Flow Requirements

The hackathon demo must prove the system improves.

Demo sequence:

1. Student A asks why a problem is not binomial.
2. Tutor uses a weak formula-first explanation.
3. Student A remains confused.
4. Pitfall Agent detects the active misconception.
5. System logs the failure.
6. Auto-Improvement Agent creates a new teaching rule.
7. Evaluation Agent creates a new regression eval.
8. Strategy score updates to penalize formula-first for this pitfall.
9. Student B with a similar profile asks a similar question.
10. Similar-Student Agent retrieves prior failure evidence.
11. SCIP selects replacement-check-first strategy.
12. Tutor gives the improved explanation.
13. Dashboard shows the full loop and before/after improvement.


22. Technical Design Principle

Keep the live voice path fast.

Only these should sit directly in the real-time path:

- Voice runtime.
- Tutor orchestrator.
- Fast context lookup.
- Fast RAG retrieval.
- Fast SCIP or heuristic decision.
- Response generation.
- Streaming TTS.

Deeper tasks should run asynchronously:

- Eval generation.
- Long-form reflection.
- Cohort updates.
- Strategy versioning.
- Dashboard analytics.
- Heavy RAG indexing.
- Auto-improvement proposals.


23. Final Framing

Tutor-Tron is a multi-agent voice tutoring system where every student interaction updates a shared learning engine. Pitfalls trigger RAG retrieval, similar-student memory, SCIP-based optimization, eval generation, and strategy updates so the system improves before the next similar student arrives.
